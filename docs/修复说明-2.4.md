## 修复 1：`api_keys.json` 缺失导致启动失败

### 现象

新克隆仓库后直接运行：

```console
$ python cnvd_recon.py --list-channels
Traceback (most recent call last):
  File "cnvd_recon.py", line 72, in load_channels
    with open(KEYS_FILE, encoding="utf-8") as f:
FileNotFoundError: [Errno 2] No such file or directory: '.../api_keys.json'
```

`校验.bat` 第 4a 步同理，自检直接中断。

### 根因

`.gitignore` 忽略了 `api_keys.json`（正确——该文件含真实 FOFA key），但 README、移植说明、使用教程三处文档都写着「包内 `api_keys.json` 是占位模板」。**占位模板从未入库**，文档描述与仓库实际内容不一致。

### 修复

- 新增入库文件 `api_keys.example.json`（全部 key 为 `REPLACE_ME`，无任何真实凭据）
- `cnvd_recon.py` 的 `_find_keys_file()` 在找不到真实配置时回退到示例模板，并返回一个「是否为示例」标志
- 新增 `keys_hint()` 统一提示：打印当前读取路径 + 两条处置建议，`exit 2`（而非抛 traceback）
- `--list-channels` 在占位模板下仍可正常工作，输出标注 `[占位模板，需复制为 api_keys.json 并填 key]`
- `校验.bat` 第 4a 步先判断文件是否存在，再判断是否为占位符，两种情况给出不同提示

### 验证

```console
$ python cnvd_recon.py --list-channels
== 已启用通道 (1 个) ==  [占位模板，需复制为 api_keys.json 并填 key]
  - primary      https://你的中转站地址  (qbase64)

$ python cnvd_recon.py --preset nvr --out x.csv
== 未找到 api_keys.json，当前读的是占位模板 api_keys.example.json ==
   读取路径: .../api_keys.example.json
   处理: 复制 api_keys.example.json 为 api_keys.json，填入你的 FOFA 中转站 base_url 和 key
   提示: 只有 recon 拉资产需要 key；--help / rules 字典 / cnvd_check.py 扫描都不需要
（exit 2）
```

`--list-presets`、`--help`、`cnvd_check.py` 等不需要 key 的路径不受影响。

## 修复 2：`--resume` 跳过零命中目标不生效

### 现象

首轮扫描 100 台，其中 90 台零命中、10 台有命中；中断后加 `--resume` 续跑，**90 台零命中目标会被全部重扫**。

### 根因

原实现从 `findings.csv` 反推已完成目标：

```python
for row in csv.DictReader(f):
    done_keys.add((row["ip"], row["port"]))
```

但 `findings.csv` 只有**命中**记录。零命中的目标永远不在集合里，因此续跑时仍会重扫。README 宣称的「断点续跑，中断不丢进度」实际只对了一半——不丢，但白跑。

### 修复

新增目标级台账 `<out>.scanned.csv`：

```csv
ip,port,hits,scanned_at,note
127.0.0.1,19999,0,2026-11-16 09:43:51,0
127.0.0.1,18080,1,2026-11-16 09:43:51,
```

- 每扫完一个目标就追加一行，**零命中也记录**（`hits=0`）
- `--resume` 以台账为准跳过已完成目标；`--ledger` 可指定台账路径
- **命中改为增量写入 findings**，与台账在同一个写锁内完成、且 findings 先写。这样进程被杀时二者保持一致：台账有记录 ⇒ 该目标命中已落盘
- 没有台账的旧 run（2.3 产生的）自动回退到原「按 findings 推导」逻辑，并打印提示说明零命中目标会被重扫

### 验证

| 场景 | 结果 |
|------|------|
| 2 台全命中，续跑 | 0 个待扫，0.07s 完成，findings 无重复 |
| 1 台命中 + 1 台端口不通，续跑 | 台账 2 行（含 `hits=0`），续跑 0 个待扫 |

## 修复 3：RTSP/FTP 探针绕过节流器（合规问题）

### 现象

README 与 SKILL.md 都承诺「单 IP 严格串行 + 间隔 ≥1s（代码级固化）」。实测服务端视角：RTSP 探针在**一条连接上连续发出 6 个 DESCRIBE 请求**，彼此间隔近乎为零。

### 根因

`Pacer` 只在 `http_probe()` 内被调用。`work()` 里 RTSP/FTP 分支是直接调用的：

```python
elif rtype == "rtsp":
    items = rtsp_probe(ip, rule.get("port", 554), args.timeout)   # 无节流
elif rtype == "ftp":
    items = ftp_probe(ip, rule.get("port", 21), args.timeout)     # 无节流
```

即「代码级固化」的合规承诺**只对 HTTP 成立**。RTSP 探针内部还会在 `RTSP_STREAMS` 上循环 DESCRIBE，同样没有任何间隔。

### 修复

- 新增 `Pacer.slot(ip)` 上下文管理器，RTSP/FTP 探针包在 `with pacer.slot(ip):` 内，与 HTTP 共用同一把 IP 锁
- `rtsp_probe()` 新增 `interval` 参数，同连接内多条 DESCRIBE 之间 `time.sleep(interval)`
- `Pacer` 的时间戳记录从 `acquire()` 移到 `release()`，间隔从**上次请求结束**时刻算起（原先从发起时刻算，实际间隔会短于设定值）
- 删除 HTTP 双差分复现前的 `time.sleep(pacer.interval)`——`acquire()` 已经负责等待，这行是重复等待

### 验证

服务端记录请求到达时间戳，标尺 = `interval 1.0`：

```
OPTIONS
DESCRIBE   间隔 1.002s
DESCRIBE   间隔 1.009s
DESCRIBE   间隔 1.007s
DESCRIBE   间隔 1.008s
DESCRIBE   间隔 1.003s
DESCRIBE   间隔 1.003s

总请求数 7 | 违反 >=1s 的间隔: 0
```

HTTP + RTSP + FTP 混排规则跑同一 IP，总耗时 3.68s（`interval=0.5`），确认三类探针全局串行、共用同一节流器。

## 修复 4：RTSP/FTP 忽略目标行端口

### 现象

`targets.csv` 里写 `10.0.0.5,8554`（非标准 RTSP 端口），探针实际去连的是 `554`，目标被漏探。

### 根因

```python
rtsp_probe(ip, rule.get("port", 554), ...)
ftp_probe(ip, rule.get("port", 21), ...)
```

端口取自规则文件的 `port` 字段，与 `targets.csv` 的行端口无关。

### 修复

新增 `probe_ports(port, rule_port)`：

- 目标行端口 == 规则端口 → 只探该端口
- 目标行端口属于常见 Web 端口（`COMMON_WEB_PORTS`，如 80/8080/443）→ 说明该行是 HTTP 资产，退回规则端口，不拿 Web 端口去连 RTSP/FTP
- 其它情况 → 先探目标行端口，再探规则端口

findings 新增 `probe_port` 列，记录**实际探测端口**；`url` 由探针按实际端口直接生成，复现时以 `url` / `probe_port` 为准。

### 验证

| 输入 | 输出 |
|------|------|
| `127.0.0.1,18554`（RTSP 服务在 18554） | 命中，`probe_port=18554`，`url=rtsp://127.0.0.1:18554/` |
| `127.0.0.1,18080`（HTTP + RTSP/FTP 规则混排） | HTTP 命中；RTSP/FTP 未误连 18080 |

## 已知遗留

- `cnvd_recon.py` 中 `urllib.parse.quote(q_enc)` 未传 `safe=''`，base64 里的 `/` 不会被编码。部分中转站可能因此解析出错，未在本版修复（缺少可复现的受影响通道样本）。
- `bing_search.py` 依赖正则刮取 Bing 的 `b_algo` 页面结构，页面改版后会失效。作为查重辅助够用，但不做加固。
