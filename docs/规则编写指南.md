# 规则编写指南 —— 端点字典 JSON 结构与判据设计

> 端点字典（`tools/rules/*.json`）是本工具包的核心资产：把「哪个路径 + 什么特征 = 未授权命中」这件事
> 沉淀成可复用的规则，跨厂商迁移。本文说明规则 JSON 的结构与判据设计方法。

---

## 1. 规则文件结构

```json
{
  "_comment": "文件说明（可选）",
  "rules": [ { ...单条规则... }, { ... } ]
}
```

`cnvd_check.py` 读取 `rules` 数组，逐条对每个目标执行。

---

## 2. 单条规则字段

### 通用字段

| 字段 | 必填 | 说明 |
|------|------|------|
| `id` | ✅ | 规则唯一标识（英文短横线命名，如 `config-json`） |
| `name` | ✅ | 人类可读名称（中文，如「Config.json 未授权读取」） |
| `type` | ✅ | 探针类型：`http` / `rtsp` / `ftp` |
| `severity` | ✅ | `high` / `mid` / `low` / `review` |
| `note` | ➖ | 备注（写危害说明 / 判据来源 / 复现要点） |

### HTTP 类型专属

| 字段 | 说明 |
|------|------|
| `method` | `GET`（默认）/ `POST` |
| `paths` | 路径数组，逐个尝试 |
| `body` | POST 的请求体（可选） |
| `content_type` | POST 的 Content-Type（可选） |
| `match_any` | **命中特征**：响应体中含任一字符串即初步命中（大小写不敏感） |
| `exclude_any` | **排除特征**：响应体中含任一字符串即丢弃（如 `login`/`401`/`404`） |
| `fake_hints` | 伪命中提示：命中这些词打 `mock=True` 标记（防误报） |
| `min_len` | 响应体最小长度（过滤空响应/错误页） |

> `match_any` 为空时：只要状态码 < 400 且过 `exclude_any` 与 `min_len` 就算命中，
> 但会打 `needs_review=True` 标记（如文件下载类端点，靠内容人工判断）。

### RTSP 类型专属

| 字段 | 说明 |
|------|------|
| `port` | RTSP 端口（默认 554） |

> 判据已内置于脚本（v2 严格版）：**必须 `DESCRIBE` 返回 200 且 SDP 含 `v=0` + `m=video/audio`**。
> 仅 OPTIONS 200 一律丢弃——这是实战返工教训固化的，不要绕过。

### FTP 类型专属

| 字段 | 说明 |
|------|------|
| `port` | FTP 端口（默认 21） |

> 判据：anonymous 登录返回 `230`。

## 3. 判据设计原则（来自实战）

### 3.1 命中要"能力点"，不要"页面能打开"

低危特征不投入：状态页、欢迎页、版本号页。

```json
// ❌ 差：版本号页谁都能看，低危不值钱
{ "match_any": ["Server Version"] }

// ✅ 好：拿到了设备唯一标识（UID/序列号）——是"未授权读数据"的能力点
{ "match_any": ["p2pUid", "devId", "SerialNumber"] }
```

### 3.2 exclude_any 是重灾区防线

设备"假装响应"很常见：返回一个登录页 HTML（含 200 状态码）。**一定要排除登录/报错特征**：

```json
"exclude_any": ["login", "unauthorized", "401", "403", "404", "forbidden"]
```

### 3.3 min_len 过滤空壳

固件空壳（40 字节的 `{}`）不算命中：

```json
"min_len": 100
```

### 3.4 fake_hints 标记占位数据

有些固件会用占位值伪装成"有数据"：

```json
"fake_hints": ["example", "test", "dummy", "000000"]
```

命中这些词 → `mock=True`，抽验环节人工复核，不计案例。

### 3.5 一条规则一个能力点

不要在一份规则里塞多个攻击面——拆开便于聚类统计和独立判级：

```json
// ✅ 好：Config.json 读 UID 一条、超级密码一条、RTSP 一条，各自独立
```

### 3.6 来源标注

新洞入库时在文件 `_comment` 或规则 `note` 里写：来源（哪个厂商/固件线）+ 判据 + 日期。例：

```json
{
  "id": "config-json",
  "note": "中维 ZWP2P 实战 2026-08-22；Config.json 未授权返回设备 UID"
}
```

### 3.7 新线起步用 rules_generic.json

面对全新产品线（无字典）：

1. 先跑 `rules_generic.json`（配置导出/backup/路径穿越/API 敏感字段/RTSP）
2. 抓 2-3 台同线设备页面挖接口（**≤10 分钟**，不要陷入单台深挖）
3. 挖到的端点结构 → 按本节原则写成新 rules 文件

## 4. 完整示例：从实战端点写成规则

实战发现：某 NVR 的 `/Config.json` 未授权可读，返回含设备 UID（`ZWP2P-XXXXXX-XXXXXX-XXXXXX`）：

```json
{
  "id": "config-json",
  "name": "Config.json 未授权读取",
  "type": "http",
  "severity": "high",
  "method": "GET",
  "paths": ["/Config.json"],
  "match_any": ["p2pUid", "devId", "SerialNumber"],
  "exclude_any": ["login", "unauthorized", "401", "403", "404", "forbidden"],
  "fake_hints": ["example", "dummy"],
  "min_len": 40,
  "note": "未授权读取设备配置含 UID → 高危；空壳 JSON/404 已由 min_len+exclude 排除"
}
```

---

## 5. 验证新规则

写好后用 `示例产出\targets_样例-脱敏.csv` 或少量已知可达目标冒烟：

```bat
python cnvd_check.py --targets 自己的小样本.csv --rules rules_你的新规则.json --out test_findings.csv
```

观察：命中是否符合预期 / 误报率 / snippet 上下文是否对得上。

> ⚠️ 只对**有授权**的目标验证你的新规则。
